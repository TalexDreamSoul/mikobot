# Bot and channel management — design

## Boundary

This change introduces a deployable bot control plane. It does not turn Persona into a transport and does not treat a channel instance as a bot. Existing Personas remain prompt identities; existing channel plugins remain transport owners.

Expected product-code boundaries:

- `nanobot/collaboration/`: durable bot, assignment, ownership, preference, and pairing-challenge contracts for local JSON and PostgreSQL.
- `nanobot/channels/`: instance-aware Pair Code interception and Weixin multi-instance management.
- `nanobot/webui/`: authenticated APIs, global/system-admin authorization, safe settings payloads, and bot/capability detail payloads.
- `webui/src/`: application-level collaboration context, sidebar switchers, localized project UI, bot/channel management, and Login & Security settings.
- Existing model-provider OAuth and MCP OAuth stay unchanged except for status links in Login & Security.

Explicit non-goals: new OAuth protocols, raw secret display, arbitrary filesystem browsing, and retroactive session reassignment.

## Domain model

### Bot

A `Bot` is a deployable assistant owned inside one organization:

- `id`
- `organization_id`
- `owner_user_id`
- `name`
- `avatar_url` (optional bounded HTTPS/data-safe URL)
- `persona_id` (optional owner-visible Persona)
- `state`: `active | disabled`
- timestamps

Organization owner/admin may manage bots. Project members may read bots assigned to projects they can access. A channel instance can belong to only one bot, avoiding ambiguous inbound routing.

### Assignments

- `BotProjectAssignment(bot_id, project_id, assigned_by_user_id, created_at_ms)`
- `BotChannelAssignment(bot_id, channel_type, instance_id, claimed_by_user_id, created_at_ms)`
- `BotProjectChannel(bot_id, project_id, channel_type, instance_id, enabled, updated_at_ms)`
- `BotCapabilityProfile(bot_id, project_id nullable, revision, settings, updated_at_ms)`

`BotProjectChannel` may reference only a channel already assigned to that bot and a project already assigned to that bot. Deleting a bot cascades its assignments/profiles but never deletes channel credentials. Removing a channel assignment disables its project routes first.

`BotCapabilityProfile.settings` accepts only bounded `skills`, `mcpServers`, and `contextMaxTokens`. A project-specific profile overrides the bot-global profile. Existing user/project `ExtensionProfile` remains for personal direct turns; migration creates a default bot and copies the existing effective selection into its initial profile.

### User preferences

Add nullable `default_organization_id` and `default_bot_id` to `User`; retain `default_project_id`. Every referenced object must be visible to the user. Sidebar changes update these preferences through authenticated mutations.

## Pair-Code challenge model

Use a purpose-bound, one-time challenge rather than trusting IDs submitted by the browser.

`PairingChallenge` fields:

- opaque challenge ID and hashed human code
- `requested_by_user_id`
- purpose: `claim_channel | assign_bot_project`
- organization, bot, project, channel type, and instance IDs required by that purpose
- expiry, verification, and consumption timestamps
- verified external sender ID

Flow:

1. WebUI requests a challenge for one exact operation and displays the short code.
2. The user sends the code in a private chat to the exact target channel instance.
3. Channel ingress intercepts it before Agent execution and verifies channel type/runtime instance and DM context.
4. Verification binds that channel sender identity to the authenticated collaboration user when claiming a channel.
5. WebUI polls the challenge and commits the operation; committing consumes it atomically.

Codes never work in groups, across users, across instances, for another purpose, after expiry, or twice. PostgreSQL uses row locking; local JSON performs verification and mutation under one file lock. Store only code hashes.

Existing sender-access Pair Codes remain supported. New assignment challenges have a distinct namespace and metadata key.

## Channel ownership and secrets

Collaboration persistence stores only `(channel_type, instance_id)` ownership/assignment references and safe status metadata. Credentials continue to live in the server-owned channel config/state files. APIs return configured-field flags and masked values only.

Self-service mutation path:

- User may configure/connect an unclaimed instance in a staging state.
- It cannot be enabled for message routing until a claim challenge succeeds.
- After claim, only the owner, organization admin, or system admin may mutate it.
- System admins retain server-wide lifecycle controls.

Channel runtime names remain generated by each plugin's `ChannelManagementSpec`; the collaboration layer stores canonical channel type and instance ID separately.

## Weixin multi-instance migration

Implement the same management adapter shape as Feishu:

- canonical `instances` array with stable IDs
- `instance_specs`, `update_instance_config`, `runtime_name`, and safe feature-instance payload callbacks
- legacy single Weixin config becomes the `default` instance without changing credentials
- each instance receives an isolated state directory under the configured state root
- connect sessions carry `instance_id` and `create | replace` mode
- QR completion writes only the selected instance
- runtime channel names are `weixin` for default and `weixin.<instance_id>` otherwise

Never allow two instances to resolve to the same state directory or runtime name.

## Authorization

### System-admin boundary

Global OIDC and raw channel configuration are readable/mutable only by:

- the local owner authenticated through the local token/password path; or
- an active OIDC session whose subject appears in `oidcAuth.adminSubjects`.

Ordinary OIDC users receive only their safe bot/channel projection. Break-glass local authentication remains available when OIDC configuration is invalid.

### Organization/project boundary

- Organization owner/admin manages organization bots.
- Bot owner or organization owner/admin claims and assigns channels.
- Project owner plus bot-management authority is required for bot-project assignment.
- RLS derives the actor from the authenticated connection; payload actor IDs are never trusted.

## OIDC settings

Add a Login & Security settings slice with:

- enabled, issuer, client ID, masked secret state, redirect URI, scopes
- token endpoint auth method
- session/flow TTL and capacities
- explicit admin subjects
- discovery/validation status and restart requirement
- summary links for existing provider and MCP OAuth sessions

Saving uses the existing path-scoped settings lock. Validate the full `OidcAuthConfig`, perform bounded discovery through the SSRF-safe OIDC client, persist atomically, and keep the currently running authenticator until restart. Never echo `client_secret`.

## Skill visibility

Return safe logical metadata only:

- source (`builtin | workspace | plugin`)
- logical root and `SKILL.md` path relative to that root
- bounded file list below the Skill directory, excluding symlink escapes, hidden credential files, oversized files, and absolute paths
- enabled/available state, requirements, and current Markdown detail

Bot detail computes effective Skills/MCP servers from bot-global and bot-project profiles without returning underlying config secrets.

## WebUI state and layout

Introduce an application-level collaboration provider used by Sidebar and ProjectsView. It owns summary, active organization, active project, active bot, preferences, refresh, and authorized mutation methods. This removes duplicate organization state from ProjectsView.

Sidebar:

- Header: logo, active-bot selector, collapse control.
- Footer: organization selector immediately above the existing Settings/connection row.
- Collapsed/mobile variants use popovers with accessible labels.

ProjectsView adds a Bots section showing assignments and enabled channel routes. Settings adds Login & Security and user-scoped Channels/Bots sections. All new strings use i18n keys.

## Persistence and migration

- Local JSON schema migration creates a default bot for each user with existing Persona/default-project relationships.
- PostgreSQL additive migration creates bot, assignment, capability, challenge, and preference structures plus forced-RLS policies and owner-preservation constraints.
- Existing Feishu instances are discoverable but unclaimed until the local owner claims or adopts them during migration.
- Existing single Weixin state becomes the default instance.

## Failure and rollback behavior

- Invalid OIDC save leaves the previous config untouched.
- Failed channel claim leaves credentials staged but disabled.
- Failed bot/project assignment consumes no challenge.
- Gateway restart failure leaves saved configuration visible with a clear restart-required/error state.
- Database migration is transactional and idempotent.
- Removing the new UI does not remove channel credentials or historical sessions.
